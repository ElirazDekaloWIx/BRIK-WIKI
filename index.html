מה BRIK באמת עושה

BRIK (בקוד: Clay / Chatooly) הוא פלטפורמה שהופכת בקשות בשפה טבעית ל-Creative Micro-Apps — כלים יצירתיים אינטראקטיביים שרצים בדפדפן: מחולל גרדיאנטים, מערכת חלקיקים, ויזואלייזר מוזיקה, כלי טיפוגרפיה קינטית וכו'. README.md

כל כלי = קנבס + פאנל פרמטרים (סליידרים, טוגלים, בוחרי צבע). הסוכן בוחר אילו פרמטרים לחשוף — וזה עצמו החלטה יצירתית. base44/functions/prompts/agentprompt.md

עקרון הליבה — "Golden Handcuffs"

חופש יצירתי וטכנולוגי מלא (כל ספרייה, כל טכניקה) — אבל מסגרת אחידה: תבנית קבועה, design system אחיד, מחויבות לפורמט פרמטרי. ה-AI לא יוצר פיסת אמנות סגורה — הוא בונה כלי שהמעצב מכוון בעצמו.

העיקרון הזה מוזכר בפרומפט של ה-Creative Director — "The AI has full creative and technological freedom, but constraints are strict." base44/functions/prompts/creativedirector.md

הארכיטקטורה הכי חשובה שעוד לא ממומשת

ToolVersion entity קיימת בסכמה — אבל אין UI שמציג אותה. base44/entities/tool-version.jsonc

זה אומר שיש לנו חצי-מימוש של version history, ו-users אין להם איך לעשות rollback. זה ה-low hanging fruit הכי ברור בארכיטקטורה — רוב העבודה כבר נעשתה.

הבעיה הארכיטקטונית הכי עמוקה

פתרון: staging writes ל-entity זמני, ואז atomic swap. או field draft_state_version שמזהה partial writes. ראה המלצות.

7 חולשות מבניות

1. הסוכן הראשי הוא מונוליט

סוכן אחד צריך להיות טוב בהכל — קריאייטיב, קוד, עיצוב, דיבוג, שיחה, domain. לכן הוא גם לא מצוין באף אחד. קונטקסט מתנפח: system prompt + skills + brief + tool schemas + history = כל קריאה prompt ענק. base44/functions/agent-chat/main.ts

2. Art Director חד-פעמי — ולא אמור להיות

רץ פעם אחת ונעלם. ב-iteration 15, כשהמשתמש אומר "זה קצת יותר מדי אגרסיבי" — אף אחד לא יודע מה "אגרסיבי" בהקשר היצירתי. בפרומפט של ה-AD עצמו כתוב: "positioned at the start and accompany it through iterations" — אבל לא ממומש. base44/functions/prompts/creativedirector.md

3. אין לולאת feedback סגורה

סוכן כותב → iframe מציג → דום. אין אימות קומפילציה, אין בדיקת ויזואל מול brief, אין סיגנל על אהבת המשתמש, אין מדידה של published/abandoned/remixed. הסוכן יורה באפלה. Skill weights סטטיים.

4. אין Critic

התוצרת נוצרת, נשלחת, נסגרת. אף אחד לא שואל: האם זה טוב?

5. Skill matching לא scalable מעבר ל-~200 skills

Keyword+stemming עובד עכשיו. יישבר כשהקטלוג גדל. base44/functions/agent-chat/prompts.ts (scoreSkillMatch)

6. Tool calls ללא guardrails

סוכן יכול לקרוא set_canvas_code בלי set_controls_schema קודם. Prompt מנסה לאכוף — LLM-ים לא טובים באכיפת רצפים. צריך runtime validation. base44/functions/agent-chat/tools.ts

7. מודל אחד לכל דבר

Conversational message → Claude Opus / GPT-4o? שורף $$. אין tiered routing. base44/functions/agent-chat/model.ts

Skills לעומק — 6 בעיות שקטות

ה-Skills system הוא אחד הרעיונות הכי טובים במוצר. והוא עדיין embryonic.

אין אנטומיה לסקיל

סקיל היום = markdown חופשי + keywords. אין מבנה. סקיל טוב חייב: when_to_use, when_NOT_to_use, conflicts_with, requires, extends, code_anchors, pitfalls, example_tools, performance_hint. base44/entities/skill.jsonc

אין רזולוציית קונפליקט

3 skills תואמים → משורשרים לתוך prompt. "Minimalist" אומרת "few elements", "Rich Detail" אומרת "many layered" → שניהם נכנסים. הסוכן מנסה לרצות את שניהם ויוצא mushy.

אין מדידת ביצועים

אילו skills יוצרים כלים שמתפרסמים? אילו קשורים לכלים נטושים? אין מי שיידע. זה מה שיכול להפוך את BRIK ללומד: Skill עם 15/20 published = priority boost. 2/20 = downgrade או בדוק.

אין versioning אמיתי

שדה version הוא מונה. אין "re-run session עם skill v3". אין A/B: "v4 מול v5 — מי ייצר כלים טובים יותר?"

אין composition hierarchy

Skill "Audio-Reactive Typography" חוזר על 80% מ-"Audio Pipeline" ו-"Typography". DRY לא קיים. Skills גדלים, חופפים, סותרים.

אין review לפני activation

Admin עולה skill עם keywords רחבים ("visual", "design") → פוגע בכל הודעה → מזהם כל prompt. אין gate.

הלב — 5 ממדי הבנה שהסוכן חסר

"הבין את הבקשה" זה baseline שכל LLM נותן. "הבנה יצירתית" זה משהו אחר — חמישה ממדים:

1. מודל משתמש (User Model) — "עם מי אני מדבר?"

רמת מומחיות, דומיין (typography / motion / generative / 3D), דפוסי העדפה אסתטיים.

היום: כל משתמש מקבל אותו prompt. "Artifacts-level understanding".

מה לעשות: Profile entity כבר קיימת — להרחיב עם user_expertise_level, preferred_aesthetic, primary_domain. למלא מהיסטוריית הכלים.

2. מודל סשן (Session Arc) — "איפה אנחנו בתהליך?"

שלב 1 (יצירה) ≠ שלב 5 (ליטוש) ≠ שלב 10 (חזרה אחרי חודש).

היום: היסטוריה גולמית, אין stage detection. סוכן עם 20 הודעות מתנהג כמו עם 2.

מה לעשות: Classifier קל (יוריסטי) שמסמן: session_stage: initial_build | refinement | polish | returning_after_gap.

3. זיכרון אסתטי (Aesthetic Memory) — "מה ה-user הזה אוהב?"

היום: אפס זיכרון חוצה-סשן. כל כלי מתחיל מאפס.

מה לעשות: אחרי כל כלי שפורסם — extract aesthetic signature (color histogram, motion energy, complexity). לאגור ב-Profile. לזרוק ל-AD ב-session הבא כ-"known preferences — confirm or override".

זה המקום שבו BRIK יכול לעקוף את Artifacts דרמטית. Artifacts לא מכיר את המשתמש — וגם לא רוצה.

4. מנוע הצעות (What's Next) — "אחרי שגמרנו, מה עכשיו?"

היום: אחרי שהכלי מוכן, הסוכן שותק.

מה לעשות: 3 הצעות בסוף כל build — Variation (אותו כלי, מוד אחר), Extension (יפגוש יפה עם Y), Remix (כלי דומה של מישהו אחר).

5. לולאת פידבק (Feedback Loop)

היום: הסוכן לא יודע אם ההצעה הייתה טובה.

מה לעשות: Implicit signals — published = positive, 10 iterations ללא publish = struggle, abandoned = negative, remixed = very positive. להזין חזרה ל-Skill weights.

8 Gotchas לא-מובנים-מאליהם

A. Prompt Drift כשאדמינים עורכים חי

עריכת SystemPrompt ב-DB ללא A/B = כל שינוי canary לכולם בו-זמנית. פסיק לא נכון → 100% מהכלים החדשים מושפעים.

B. Tool Schema Exposure בלוף

מעצב בונה כלי ל-client / קהל (wedding invite, kid activity, game demo). Embed + share קריטיים. נדרש: ToolEmbed עם access control + branded shell.

Pattern C — "כלי ל-one-time event / פיץ'"

כלי לאירוע ספציפי (pitch, launch, presentation). Speed-to-quality חשוב יותר מ-retention. נדרש: presets, templates, fast iteration.

Pattern D — "כלי explorative / play / learning"

יוצר בונה כלי כדי ללמוד / לחקור / לשחק. Community + remix מזינים את זה. נדרש: gallery robust, remix smooth, credits למקור.

2. 5 יכולות שחזרו ברוב הקלאסטרים

  • Brand Kit / Palette persistence — 8 מתוך 14 קלאסטרים ציינו שימוש חוזר ב-colors/fonts. BRIK רמה 1 — חיוני.
  • Export קיט שלם — לא רק PNG אחד, אלא סדרה: 10 variations של thumbnail, 5 platforms (IG/TikTok/Twitter). BRIK: Export Presets.
  • Presets "dogmatic" — כל קלאסטר רוצה "התחל מזה, אל תמציא מאפס". BRIK רמה 2 — Preset library per tool type.
  • Brand-safe / client-safe outputs — B2B crowd רוצה watermark, attribution, white-label. ToolEmbed features.
  • Quick iteration + pin version — "נסה 5 variations, אני אחזור למס' 3". Version UI — כבר ב-roadmap.

3. 3 גאפים שרק עכשיו התבררו

Gap 1 — Video export איכותי לא-דיסקרטי

הרבה מהקלאסטרים (motion, social, VJ, installation) דורשים video quality-first. 60fps, 4K, lossless codec. ChatoolyCanvas היום תומך — אבל לא ברור אם quality מספיק ל-broadcast / festival. אימות דרוש.

Typography, Editorial, Type designers — דורשים variable fonts, OpenType features, kerning control. BRIK היום בסיסי. דורש BRIK חדש: Professional Typography Engine.

Gap 3 — Physical output / print-ready

Fashion, Industrial, Architecture, Print — דורשים CMYK, high-DPI, vector export, print marks. דורש Print Export Pipeline.

מחקר R1 · ארכיטקטורת סוכנים

מחקר עומק — ארכיטקטורות סוכנים

השוואה יסודית של כל תבנית ארכיטקטונית מרכזית לבניית סוכני LLM, מבוססת על מאמרים אקדמיים ומעבדות תעשייה מובילות. התשובה לשאלה "יש תבנית שמנצחת את כולן?" — והמשמעות ל-BRIK.

פסק הדין בשורה — אחרי המחקר

אין תבנית ש"מנצחת" את כולן. הציר הדומיננטי הוא task determinism × verifiability × cost. לפי Anthropic [1] והביקורת החשובה של Kapoor et al. [14], הראיות מצביעות על **workflow פשוט עם verifier זול ו-memory persistent** — לא multi-agent hierarchy. לגבי BRIK ספציפית: הכיוון הוא Router + Persistent Brief + Evaluator-Optimizer + Agentic RAG, לא Multi-Agent Pipeline.

עדכון R2 — Round 2 (מעמיק יותר עם citations חיים)

לאחר פידבק שהמחקר לא היה מעמיק מספיק, בוצע סיבוב שני עם WebSearch + WebFetch חי. הממצאים החדשים:

  • Anthropic עברה ב-Sep 2025 ל-"Context Engineering" — מסגרת חדשה שממסגרת מחדש את כל הדיון [A1]. "The frontier has moved from which agent pattern is best to how do you engineer the context a single strong agent sees."
  • Multi-agent אצל Anthropic מדווח 15× עלות tokens ומשתלם רק ל-"breadth-first queries with parallel sub-questions" [A2]. BRIK היא exactly hot ברירת המחדל שלא משתלמת שם.
  • Prompt Caching (Anthropic) — 0.1× קריאה, 85% הורדת latency על prefix של 100K tokens [A3]. זה ה-#1 השיפור שאפשר לעשות היום.
  • Persona-conditioned "Spark" agents — +4.1 diversity על סקאלה של 10 (מדד מחקר מנוכס) [A4]. מתאים בדיוק ל-14 קלאסטרי ה-designers של BRIK.
  • Skill matching: keyword→embeddings — 5000ms → 100ms routing latency לפי benchmarks מפורסמים.
  • Code execution with MCP — Anthropic דוחפת ל-pattern חדש שבו tools = code execution sandbox, לא function calls [A5]. BRIK צריך לבחון אם זה משפר את ה-tool layer הנוכחי.
  • LangGraph 1.0 released — checkpointing, durable execution, human-in-the-loop כ-first-class. רלוונטי כ-alternative runtime למ-Mastra.
  • OpenAI AgentKit (Dec 2025) — SDK רשמי חדש מ-OpenAI, חלופה ל-Mastra.

10 המלצות קונקרטיות מבוססות מקורות (מתוך R1 v2): Prompt caching → Embeddings skill matching → Tiered model routing → Persistent Planning Brief (MemGPT-style) → Evaluator-Optimizer loop with cheap verifiers → Skill performance telemetry → Tool-result summarization → Semantic router → Voyager-style skill library → Constitutional style pass.

ציר הבחירה — חמשת הממדים

בחירת ארכיטקטורת סוכן היא trade-off על 5 צירים — לא "מה הכי טוב" אלא "מה מתאים ל-workload":

  • Task determinism — האם ה-flow צפוי מראש? צפוי → workflow; לא → agent autonomy.
  • Verifiability — האם יש signal אם התוצאה טובה? (compile? render? pass test?) יש → יכול לעשות self-correction.
  • Horizon length — כמה "turns" לפתרון? ארוך → memory חשוב.
  • Cost tolerance — כמה $ מוכנים לשרוף ב-token? Production = קמצני.
  • Debuggability — כשזה נשבר, האם אפשר להבין למה?

החלוקה המכריעה של Anthropic [1]

Workflow = orchestrate LLM דרך code paths מוגדרים מראש. Agent = ה-LLM מנווט לבד.

המסקנה של Anthropic: רוב מערכות production לא צריכות "agents" — הן צריכות workflows. אוטונומיה צריכה להיות מורווחת מהעמימות של המשימה, לא מונחת כברירת-מחדל. זה מנוגד ישירות ל-AutoGen ו-MetaGPT שמתחילים multi-agent by default.

ל-BRIK: שדרוג ה-matching הוא הצעד הכי חשוב.

1.18 Agentic RAG★ קריטי

ה-agent מחפש ידע רלוונטי. שתי אסכולות — retrieve פעם אחת upfront (זול, פשוט), או iteratively. [22]

ל-BRIK: מאוד גבוהה. Skills = ה-corpus שלכם. לעבור מ-keyword+stemming ל-embedding retrieval על תיאורי skills; להזריק top-K לפי semantic match. זה גם מה שגורם ל->200 skills לעבוד.

1.22 Evaluator-Optimizer (Verifier + Critic loops)★★★ TOP

Generator → verifier זול מעריך → אם נכשל, generator מתקן עם ה-feedback של ה-verifier. [1]

ל-BRIK: ההתאמה הכי גבוהה. אפשר לאמת בזול:

  • ה-code מתפרס?
  • אין runtime error ב-headless canvas boot?
  • ה-controls schema validates?
  • אין undefined symbols?
  • tool schema JSON-parses?

כל אחד מאלה תופס failure mode אמיתי. זו התוספת הכי חשובה ל-BRIK.

1.23 Long-Horizon Memory (MemGPT / Voyager / Generative Agents)★★ מאוד חשוב

MemGPT — virtual memory, tiered main/archival. [10]
Voyager — lifelong learning עם skill library גדלה של patterns מצליחים. [11]
Generative Agents — Park et al., Stanford; memory stream עם importance/recency/relevance + reflection. [12]

ל-BRIK: מאוד גבוהה. "Brief dies after message 1" הוא בדיוק בעיית MemGPT. שני מהלכים קונקרטיים:

  1. Persistent Planning Brief — JSON מובנה, מוזרק כל turn, מתעדכן דרך update_brief tool.
  2. Voyager-style skill library — patterns מצליחים נצברים; נשלפים לפי similarity. זה ה"aesthetic memory" ש-BRIK צריך להיות לו.

סינתזה — 5 הארכיטקטורות המתאימות ביותר ל-BRIK (מדורגות)

★1

Router + Persistent Brief + Evaluator-Optimizer (מהלך הדרגתי)

מה זה: שומרים על Triage → Creative Coding הקיים. מחליפים את ה-Art Director החד-פעמי ב-brief מובנה persistent שמוזרק כל turn. מוסיפים critic זול ברמת הקוד (compile/render/schema-validate) שמפעיל retry אחד בכישלון.

Migration:

  1. הגדרת PlanningBrief schema (style tokens, intent, constraints, user aesthetic prefs).
  2. Art Director כותב ל-brief בהודעה 1 ויכול לעדכן דרך update_brief tool.
  3. Creative Coding Agent מקבל את ה-brief הנוכחי בכל turn.
  4. אחרי tool calls: parse AST, validate schema, headless render smoke test. על failure → retry אחד עם ה-error כ-feedback.
  5. Cap ב-retry אחד (Anthropic: autonomy bounded). [1]

מקורות: [1] workflow + evaluator-optimizer; [10] persistent memory; [3] Reflexion עם verifier אמיתי.

★2

Router + Semantic Skill Retrieval (agentic RAG)

החלפת keyword/stemming scoring ב-embeddings. Index skill descriptions + exemplar outputs. Retrieve top-K לפי cosine similarity למסר + brief.

Migration: Embed skills offline (פעם אחת). בבקשה — embed המסר, retrieve top-K, inject. Scales ל-אלפי skills. שכבה תחת #1.

מקור: [22] Self-RAG.

★3

Voyager-style Skill Library (aesthetic memory לאורך זמן)

כשכלי שנוצר מאומץ על ידי המשתמש (מפורסם / רימקס), שמור את ה-artifact (code + brief context) ב-library retrievable. בקשות עתידיות שולפות similar prior successes כ-in-context exemplars.

Migration: הוסף success signal implicit (משתמש ממשיך מול rests; publishes). Embed successful tools. Retrieve כ-few-shot examples. זה "aesthetic memory" המדובר.

מקור: [11] Voyager.

★4

LangGraph (או equivalent) — state machine ל-session durability

להעביר את ה-session ל-state graph explicit עם checkpoints כדי ש-failures מיד-session resume. לא pattern חדש — ה-runtime הנכון לאירוח patterns 1-3.

Migration: להעריך אם Mastra primitives מספיקים; אם לא — LangGraph checkpointer.

מקור: [21].

★5

Constitutional Style Pass (אופציונלי, win זול)

Anthropic-style "brand constitution" critique pass על code/copy כדי לאכוף עקרונות אסתטיים ("אין default component libraries נראים", "controls labels sentence case").

Migration: קריאה אחת נוספת עם רשימת עקרונות. Gate ב-heuristic.

מקור: [6].

מה BRIK לא צריך לעשות

  • MetaGPT / AutoGen-style hierarchy — cost blowup, debug nightmare, אין task decomposition שדורש את זה. [8] [7] [14]
  • Tree of Thoughts — אין value function לאסתטיקה. [5]
  • Debate — אסתטיקה לא adversarial. [18]
  • Self-Consistency voting — לא-מוגדר ב-creative outputs. [24]
  • Self-Refine ללא verifier — Huang et al. מראים שיכול לפגוע. [15]
  • אוטונומיה מלאה — [1] + [14]

Anti-patterns — מה להימנע

Adding agents because frameworks make it easy

כל agent חדש = failure mode חדש.

Generator + judge מאותו מודל

Self-preference bias. [23]

Unbounded retry loops

תמיד cap. Anthropic explicit. [1]

Free-text בין-agents messages

העברת state מובנה — לא chat logs. פחות drift, פחות tokens.

אמונה ב-benchmark leaderboards

Kapoor et al. חובה: AgentBench/GAIA results לא מתחדשים בפרודקשן; cost כמעט אף פעם לא מדווח. [14]

אופטימיזציית ארכיטקטורה לפני Prompt Caching

30K tokens חוזרים, ללא caching? הפעלה של Anthropic prompt caching = 90% חיסכון על cached prefix. [26] זה מטרד כל רווח ארכיטקטוני. לעשות את זה ראשון.

Long ReAct scaffolds על מודלים מודרניים

native tool-use כבר מבצע reasoning — "Thought:" preamble לעיתים קרובות dead weight. [1]

המהלך הכי חשוב היחיד

הפעלת Prompt Caching, ואז הוספת Evaluator-Optimizer loop. כל השאר משני. ביחד — לפי הערכות Anthropic [26] ו-evaluator-optimizer pattern [1] — זה חיסכון 60-80% בעלות + העלאת איכות משמעותית, ללא complexity של multi-agent.

תבניות חדשות לעקוב ב-2025-2026

  • Computer-Use / Agent-Computer Interfaces — Anthropic Computer Use (Oct 2024), OpenAI Operator (Jan 2025). רלוונטי אם BRIK יצטרך שהסוכן ישתמש בכלי שבונה כדי לאמת ויזואלית.
  • Agentic RAG עם query planning — Self-RAG [22] + ReAct-RAG hybrids.
  • Deep research agents — OpenAI Deep Research, Google, Perplexity. Pattern: orchestrator + web workers + citation extractor.
  • Eval-first pipelines — Arize, Braintrust, LangSmith. התעשייה מודה ש-Kapoor et al. צדקו. [14]
  • SWE-agent paper (Yang et al., Princeton) — tool design חשוב יותר מארכיטקטורה. [13]
  • Prompt caching — Anthropic (Aug 24), OpenAI (Oct 24), Gemini. לא pattern — אבל המהלך הכי חוסך עלות. [26]

שורה תחתונה ל-BRIK, פשוט

אתם לא under-architected; אתם under-instrumented. שלחו prompt caching, הפכו את ה-Planning Brief ל-persistent, הוסיפו verifier זול עם retry אחד, העבירו skill matching ל-embeddings, והתחילו Voyager-style library של successful tools ל-aesthetic memory. התנגדו לפיתוי ה-multi-agent — הספרות (Anthropic [1], Kapoor [14], Huang [15]) מתכנסת לעמדה ש-more agents זה בד"כ צעד אחורה בפרודקשן.

המלצה: B2B זה fork-in-road. Motion של agency/enterprise ל-BRIK = business defensible $10-30M ARR ב-24 חודשים, דורש dedicated GTM + product work.

אלה לא כישלונות — אלה בחירות. המשימה של BRIK היא לבחור terrain שבו השילוב שלה decisive, לא להילחם בכל חזית.

BRIK יכולה לקפוץ רמה שלמה בתוך חצי שנה עם 4 שכבות חדשות בארכיטקטורה: (1) WebGPU renderer mode (Three.js TSL) עם compute shaders; (2) Transformers.js v3 ל-ML בדפדפן (SAM 2, Depth Anything, MediaPipe); (3) Asset Providers layer (Poly Haven, AmbientCG, Pexels, Freesound, Iconify, Google Fonts — unified API); (4) 3-tier Inference Router (client-side → fal.ai real-time → fal/Replicate queue). כל זה תחת רישוי commercial-clean שאומת.

1. סיכום מנהלים

BRIK (הידועה בקוד גם כ-Clay / Chatooly) היא פלטפורמת AI שמפיקה "creative micro-apps" מבקשות בשפה טבעית. המוצר חי בפרודקשן, משרת משתמשים פעילים, ומיוצר על Base44 (BaaS של Wix). הפלט = כלי אינטראקטיבי (canvas + controls sidebar) שניתן לשמור, לפרסם, לעשות embed, ולרמקס.

הסבר מעמיק — למה דווקא ה-4 האלה קודמים

הפרדוקס של security ב-AI product

רוב ה-SaaS dev-tools צוברים חוב security בהדרגה. ב-BRIK זה הפוך: כל יום שעובר גלריית הכלים הפומביים גדלה. כל כלי הוא "שדה פעולה" XSS פוטנציאלי. משתמש זדוני אחד שמכיר את ה-template literal injection יכול היום לפרסם כלי שסורק localStorage של אלפי צופים. הסיכון מצטבר לוגריתמית ככל שגדלה ה-gallery, לא ליניארית. לכן #1 ו-#2 קודמים לכל שיפור מוצר — אחרי 1000 כלים זה כבר קשה לתקן בלי break.

למה Rate limiting (#3) חייב להיות לפני מונטיזציה

ללא rate limiting לא ניתן לתמחר. ללא תמחור לא ניתן לפתוח ל-public scale. זה גם שחרר את המערכת ל-abuse: אפשר לשרוף $10K בלילה דרך חשבון אחד. יתר על כן — הוספת rate limiting אחרי שמשתמשים כבר רגילים ל-unlimited היא שינוי UX כואב ("פתאום יש לי limits"). עכשיו כשהבסיס קטן — ה-friction מינימלי.

למה #5 (throw במקום console.error) זה "טריק של שעות עם ROI עצום"

כרגע ב-session.ts יש catch { console.error(...) } — השגיאה מתנדפת, המשתמש רואה "נשמר" והמידע באמת אבד. זו "אובדן מידע שקט". רק מעבר ל-throw יגרום ל-SSE להעביר שגיאה ל-client, ל-UI להציג "נכשל, נסה שוב", ולמשתמש לא לאבד 10 דקות עבודה. זה שורת קוד אחת. האימפקט עצום ביחס לעלות.

המסגרת הכללית: הפעולות הנוספות (6-10) פותרות בעיות חשובות אבל לא בעיות שעלולות לבעור. ה-4 הראשונות הן הבסיס שבלעדיו כל השקעה במוצר נמצאת על קרקע לא יציבה.

הסבר מעמיק — Q7 (Base44 lock-in) — איך להחליט

Vendor lock-in הוא עקומה, לא בינארי

אופציות מעשיות

Option A — להישאר ולהתחייב: לבנות על Base44 במלוא העוצמה. יתרון: מהירות. סיכון: ב-10K MAU כל פיצ' מיוחד הופך ל-lock-in נוסף.

Option C — Gradual migration: להעביר חתיכות קריטיות (auth, file storage) ל-Supabase/Clerk/S3 ישירות. עלות: חודשים. תועלת: שליטה מלאה.

השאלה הנכונה: "אם BRIK תרצה לעבור off Base44 ב-2027, כמה כואב יהיה?" אם חודשיים — להישאר. אם חצי שנה+ — להתחיל ב-Option B עכשיו.

טרמינולוגיה מוצעת עבור שכבת ה"יכולות המוצהרות" — יכולות שהפלטפורמה מספקת בדעה חזקה. מובחן מ-Agent tools ומ-Tool entity.
Creative Director / Art Director
סוכן AI ראשון שרץ על בקשה חדשה. מייצר Planning Brief מובנה (Core Intent, Interpretation, Technical Flags, Decision Hierarchy). base44/functions/prompts/creativedirector.md
Creative Coding Agent
הסוכן הראשי שבונה את הכלי. Mastra-based. יש לו 11 tool calls. base44/functions/agent-chat/agents.ts
Golden Handcuffs
עיקרון הליבה של BRIK — חופש יצירתי מלא בתוך מסגרת אחידה. הפלט תמיד פרמטרי. base44/functions/prompts/creativedirector.md
Parametric micro-app
היחידה האטומית של BRIK — כלי קטן שמורכב מ-canvas + controls schema. המשתמש שולט דרך הפרמטרים, לא דרך canvas.
Assembler
מודול שלוקח {canvas_code, controls_schema, libraries, custom_css} ומרכיב HTML שלם ל-iframe. src/canvas/assembler.ts
ChatoolyCanvas / ChatoolyControls
שתי ספריות runtime שמוזרקות לכל iframe. הראשונה מטפלת ב-export/recording/background, השנייה מספקת 25+ widgets. src/canvas/runtime.ts
Draft / Published split
כל Tool מחזיקה שתי גרסאות מקבילות — הסוכן כותב ל-draft, הפרסום מעתיק ל-published. base44/entities/tool.jsonc
bakeControlDefaults
בפרסום, עדכון ה-default של כל control בסכמה לערכים החיים. גורם ל-remix להתחיל מהמצב שהיוצר ראה.
SSE — Server-Sent Events
פרוטוקול ה-streaming של BRIK — הסוכן מזרים updates חיים ל-UI. base44/functions/agent-chat/main.ts:138
Skill
יחידת ידע חיצונית לסוכן. markdown + keywords + modes. מוזרקת ל-system prompt כשתואמת. base44/entities/skill.jsonc
Decision Hierarchy (Levels 0-3)
מסגרת של ה-Art Director לסיווג החלטות יצירתיות: Not specified / User-specified / Convention / Creative interpretation.
3 Decision Tests
מסגרת הערכה של פיצ'רים: Thesis Test (מחזק parametric?), Moat Test (מחזק Skills/Community/Memory?), Golden Handcuffs Test (נותן או לוקח בחירה?).
6 Personas
A: Creative Tech (7/10) · B: Designer-Coder (9/10) · C: No-Code Designer (4/10) · D: Creative Director (6/10) · E: Tinkerer (8/10) · F: AI-Native (5/10)
5 Understanding Dimensions
המימדים שהסוכן חסר: User Model, Session Arc, Aesthetic Memory, What's Next Engine, Feedback Loop.
